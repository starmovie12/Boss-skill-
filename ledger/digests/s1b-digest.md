## E. Load and abuse stress plan (S1-2340, S1-2813, S1-3612 | AUDIT)
- Two framing questions per state-changing flow: under peak concurrency where is the bottleneck; under hostile traffic where is the leak.
- Cohorts, 60s sustained. Legitimate 10,000: 8,000 readers (browse/scroll/query, no writes); 1,000 writers at uniform rate; 500 race probers (parallel writes to one shared record); 500 auth flows (login, logout, token refresh). Hostile 1,000: 200 injection payloads; 200 sequential-id enumeration; 200 rate-limit boundary tests; 100 decoy-route pings; 100 prompt-injection on AI routes; 100 credential stuffing; 100 cross-scope channel hijack.
- Pass criteria: p95 < 500ms; p99 < 1500ms; legitimate error rate < 0.5%; zero data corruption; all hostile actors flagged within 60s and blocked within 5min; zero false positives on legitimate bursts; memory growth under 100MB over the run.
- Run-time observation: live concurrency, messages/s, block rate, p99, memory; error alarm at 0.5%. Rollback rule: any failed criterion blocks release. CI: nightly plus on every change touching state-changing paths.
- Honesty fix: the source lets a mental run "pass" numeric criteria. Reasoned walk-through yields risks, not numbers; percentiles and detection rates need a real run. "100% detection with zero false positives" is not a credible absolute.

## H. Realtime and data reference (REF)
- [S1-1673] Private/presence channel auth is a server route: confirm session, parse the scope out of the channel name, compare with the caller's membership, refuse on mismatch, log the attempt.
- [S1-1673] Hot record (more than about one write per second): N counter shards (source uses 32), increment a random shard, sum all on read.
- [S1-1673] Presence: heartbeat 30s, stale after 90s, sweep every 60s, timestamps set by the server. Reconnect: 1s base doubling to a 30s cap plus random jitter (source comment says plus-or-minus 30% but the code only adds, and can exceed the cap).
- [S1-2243] Publish pipeline: unknown event name rejected -> payload validated by the event's schema -> personal data stripped (emails, phones, internal ids) -> publish to scoped channel -> log event and payload size. Event names dot-namespaced lowercase.
- [S1-2243, S1-2639] Caps: 10K subscribers per channel then split into sub-channels; 100K then multi-region provider. Caps differ across units (10K, 5K, 1K), so treat as illustrative.
- [S1-2314] Edge runtime: Web-standard APIs only, no filesystem/child processes; budgets cold start 50ms, bundle 1MB, CPU 50ms per request are the source's figures and may be stale; check the provider's current limits.
