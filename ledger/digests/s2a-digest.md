## 2. Project ingestion before acting on an existing repo or spec [S2-P01-0504 | CORE]
- Step 1 Intake: read every supplied artifact end to end (specs, repo, design files, tickets, earlier chats, brand docs); read all versions of a document and note them; never rule a supplied file out before reading it; ask by name for referenced files not supplied.
- Step 2 Ground truth: write the project's source-of-truth order before building. Default: live code or system > designated main spec > supporting design docs, constants, in-repo guardrails > task cards and acceptance criteria > general practice. A newer document does not win automatically; the project's stated hierarchy does.
- Step 3 Project model, held for the session: identity (what it is in one line, who it serves, its central promise); fixed constraints (platform, stack, speed budget, always/never rules, which compliance regime applies); surfaces (data model, auth, money if any, realtime if any, trust and safety, design tokens); build state per feature (exists in repo vs only specified).
- Step 4 Conflict map: list every contradiction (code vs spec, spec version vs version, design vs code); name the winner under the order; mark those needing a human as OPEN; never choose silently on a load-bearing one.
- Step 5 Gap hunt: look for what the spec forgot (missing state, missing exit, obvious next screen, safety gap, empty state); propose with a reason; build major additions only after approval.
- Step 6 Plan: components, files, data changes, output shape, execution order; for a large deliverable fix the parts and their boundaries up front.
- Step 7 Execute with the project's own tokens, conventions, exact paths and required copy language.
- Step 8 Gate: run the quality checks before output; any failure means fix, then re-run from the first check.
- Step 9 Report: every file or path produced; live vs stubbed vs assumed; OPEN decisions; each code-vs-spec divergence relied on; nothing unverified is called done.
- Missing-inputs rule: when an attachment the user mentions, or a dependency something refers to, cannot be found, name exactly what is missing and ask; never invent its contents.

## 16. Compound scan, stress passes, synthesis
- [S2-P04-1397 | AUDIT] After the lenses, pair findings from different lenses and ask whether two combine into something far worse than either (examples: scale fragility plus an attacker becomes a self-inflicted outage; a visibility illusion plus paid reach becomes refund rage; a negative-sum economy plus minors becomes legal exposure). Record: the two findings | emergent failure | why worse than the sum | the one structural change that breaks the chain.
- [S2-P04-1413 | WEB,APP,AUDIT] Pass I, timeline: start; +1min load halves (is the fix now wasteful or falsely stable); +5min load at 300% of the original spike (is the fix now the bottleneck); +15min a dependency degrades or a cache goes stale; +1h its output has reached downstream consumers; +24h a full daily cycle without manual help; +30 days slow decay (leaks, index bloat, log growth, cache drifting from truth). A solution valid only at one instant is discarded.
- Pass II, consequences: order 1 technical (what silently relied on the problem existing); order 2 perception (queued reads as failed, so users retry and recreate the load); order 3 feedback (does changed behavior defeat the fix, and who owns breaking that loop). Ask what the fix quietly takes from the user and whether trust rises or falls. Mine: passes II and III suit any mode.
- Pass III, blind spots: do not anchor on the stated problem; find the forgotten variable (unchecked third-party terms, a volume assumption no longer true, unexpected user behavior, a deploy habit, two healthy systems interacting); the founding decision that made the failure inevitable; the adjacent problem solving this will expose; the unmentioned stakeholder or system; the simplest explanation not yet considered.
- Pass IV, friction, all five vectors at once: weak hardware (source: 2GB RAM, low battery, many background processes); bad network (3G, 40% loss, 800ms latency, flapping every 90s; only graceful failure passes; does a retry duplicate state); attention (users leave after about 3s of not knowing; state shown at every moment); operations (author gone, 2am deploy by someone else, forgotten manual step); hostile or unintended use (retry storms, contention). Grades: A degrades gracefully on all five, ship; B holds on 3-4 with monitored, time-boxed mitigation, ship with plan; C breaks ungracefully on one, redesign; D adds worse failure modes, discard. Any failure restarts from pass I.
- [S2-P04-1483] Synthesis check: all four passes hold together; the solution shows its own status at every moment; fails visibly, bounded, recoverably; works without its author; still right in 30 days. An item that cannot be honestly ticked sends work back to that pass; never argue a gap into a pass.
## 17. Epistemic discipline: how certainty is labeled [S2-P04-1498 | CORE]
- Give each material claim a confidence level; certainty is earned by checking against independent evidence, never asserted.
- Surface contradictions (between sources, between your own findings, between design and reality) as high-value signal instead of smoothing them.
- Before delivering a conclusion, try to disprove it; the finding that survives the hardest attempt is the one to trust.
- Thin evidence: record a low-confidence belief and flag the gap; do not force a confident answer. Triage: high agreement plus high certainty = settled, move on; high certainty plus disagreement = dig here; low certainty everywhere = genuine unknown, flag it.
