# s3b digest: design-system references, data tables, scripts (65 whole-file units, S3-F:*)
Legend. DS:x = S3-F:references/design-system/x.md; R:x = S3-F:references/x.md; D:x = S3-F:data/x; ST:x = S3-F:data/stacks/x.csv; SC:x = S3-F:scripts/x.py. Modes WEB, APP, AUDIT, PROMPT, CORE. "(src)" = the source's own number; the source itself marks most numbers as unverified author heuristics.

## 1. Token tiers (the method, not the values) [DS:token-architecture, DS:primitive-tokens, DS:semantic-tokens, DS:component-tokens, R:visual-tokens-recipes] WEB,APP
- Primitive tier: raw values only, no meaning (colour ramps 50-950, spacing on a 4px base, type sizes, leading, weights, tracking, radius, shadow, duration, z-index). Changed rarely.
- Semantic tier: purpose aliases that may reference ONLY primitives. Every fill role has a paired foreground role (primary + primary-foreground). Roles: background/foreground, card, popover, primary (+hover, +active), secondary, muted, accent, destructive, success/warning/error/info, border, input, ring; spacing (component xs-lg, section sm-lg, page x/y); type (heading, body, label, caption); interaction (ring width, ring offset, disabled opacity).
- Component tier: references ONLY semantic tokens, one set per variant and per state (bg, fg, hover-bg, active-bg, border, focus ring, error, disabled). Size variants change padding, height and font only; colour is shared. (Source slips: its component files point spacing/radius straight at primitives; decide whether sizes may skip the semantic tier and say so.)
- Rule to verify: components cite token names only; a raw hex/px appears once, in a palette table (token, primitive seed, light value, dark value, paired text/surface, measured ratio, evidence label). Flag any component rule that cites a primitive colour step directly.
- Naming: --category-item-variant-state (categories: color, space, font-size, radius, shadow, duration). Files: primitives, semantic, components, index (or one file with layer comments). Optional JSON form with value and type per token. Migration from flat tokens: extract raw values to primitives, alias them as semantic roles, point component tokens at the roles.
- Dark mode is a DELTA: one dark block overriding semantic tokens only (surfaces, foregrounds, muted, secondary, accent, border, input). Primitives and component tokens unchanged; brand role normally unchanged, status roles change only if contrast fails. Verify: the dark block introduces no new raw values beyond surface ramps.
- Surface ladder method (R:visual-tokens-recipes): base, surface, elevated, sunken. Light base 96-99% lightness; dark base 4-8% (src), never pure black unless an OLED direction; in dark, each elevation step is 3-6% lighter (src); accent in dark 10-15% lighter and less saturated so it does not glow (src).
- Every token carries a may-use and may-not-use rule (e.g. accent fill: primary action, active indicator, under ~10% of screen; never body text, big backgrounds, destructive buttons, or two primaries on one screen).
- Text role floors: primary/secondary/meaningful tertiary text 4.5:1 against their own surface (target 7:1 for primary), non-text cues 3:1, disabled text 0.38-0.5 opacity plus a one-line reason why it is disabled; hairline borders low-alpha, control borders 3:1 when the boundary carries meaning.

## 2. States and variants [DS:states-and-variants, DS:component-specs, R:visual-tokens-recipes, D:ux-guidelines] WEB,APP,AUDIT
- Six states per interactive component: default, hover, focus, active, disabled, loading (plus error for inputs, selected for rows/chips, read-only distinct from disabled). Precedence when several apply: disabled > loading > active > focus > hover > default.
- Focus: visible ring on keyboard focus only, built as two layers (background-coloured offset 2px, then 2px ring) (src); container shows focus-within; error state swaps the ring to the error colour; ring contrast 3:1.
- Disabled: reduced opacity, no pointer events, not-allowed cursor, muted fill; semantic disabled attribute; prefer keeping disabled text legible and saying why.
- Loading: spinner placement by component (button replaces icon or centres and locks width, input trailing, card centre overlay, page viewport centre); content dims; busy attribute plus screen-reader text; blocks double submit; over ~1s use a content-shaped skeleton, never a full-screen blocking spinner (src).
- Error: border + text in error colour + icon, message directly below the field, one-line fix, linked to the field for assistive tech, live alert; clears on valid input; never colour alone.
- Transitions: colour/background ~150ms ease-in-out, transform/shadow ~200ms ease-out (src); pressed feedback ~100ms with slight scale (src). Variant pattern: each component declares local custom properties; modifier classes override only those (colour variants: primary, secondary, destructive; size variants sm/default/lg).
- Action rank -> button variant: filled = the one primary action per screen; tonal/secondary; outline/ghost = tertiary; link = navigation; destructive = outline at first, filled only inside the confirm dialog, at least 16px (src) away from the primary; reversible destroy gets undo, irreversible gets explicit confirm.
- Hit areas: primary action 48px+ on touch (src); chips may look 28-32px tall but their target is 48px; list rows 56 one-line / 64-72 two-line (src); tables: text left, numbers and row actions right, status centred; densities compact/default/comfortable.
- Dialog anatomy: title + close, scrollable body, footer with cancel before confirm; full width minus margins on mobile. Empty state: one heading, one line, one action in thumb reach. Snackbar never steals focus.

## 3. Typography rules (not pairings) [R:typography-rules, R:visual-tokens-recipes, D:ux-guidelines] WEB,APP
- Scale logic: a short named ladder (display, number-hero, title, heading, body, body-strong, label, caption); at most 4 sizes and 3 weights per screen (src); display at most once per screen and never in dialogs, settings or dense dashboards.
- Floors: mobile body 16px (also prevents mobile browser auto-zoom on inputs), nothing under 12px (src). Weights: heading 600-700, body 400, label 500, button 600 (src). Never bold whole paragraphs.
- Line height: body 1.5-1.65, display ~1.1-1.15 for Latin (src). Measure: 35-60 characters per line on phones, 60-75 on desktop (src).
- Tracking: tighten only large display text; labels and captions slightly open; zero for body. Numbers in tables, prices, amounts, timers: tabular numerals.
- Loading: swap or optional font display; preload only critical weights; at most two families; a pairing contrasts an expressive heading face with a calm readable body face (single-family pairs use weight steps).
- Script handling (Devanagari and any non-Latin): tracking 0, no negative tracking, no caps transform, no italics; body/label line height 1.5-1.6, display/title at least 1.3 (src); budget extra height inside buttons, chips and inputs.

## 4. Script-coverage check algorithm [R:typography-rules, SC:check_devanagari, D:google-fonts.csv] WEB,APP,AUDIT
- Step 1: never infer coverage from the font name. Look up the exact family in a font catalog and split its subsets field; for a local/custom build inspect the font file for the Unicode block (Devanagari 0900-097F plus extended A8E0-A8FF) and the script's shaping tables.
- Outcome states: listed = candidate; not listed = "unverified in this snapshot", not "absent"; unknown family = fuzzy-suggest close names, coverage unverified. Step 2: if missing, partial or unverified, add an explicit script companion font in the stack after the Latin font and before the system fallback.
- Step 3: render real and mixed strings and check five points: conjuncts join correctly; vowel signs above/below attach without collisions; line height per section 3; no clipping of marks inside fixed-height buttons, chips, inputs or overflow-hidden boxes; mixed-script baseline, x-height and stroke weight look matched on one line.
- Step 4: label honestly: tool run + render = verified; catalog only = from-data with rendering not-tested.

## 5. Contrast check algorithm [SC:contrast_check, SC:validate_data, DS:states-and-variants] CORE for WEB,APP,AUDIT
- Parse hex (3 or 6 digits); if foreground has alpha, composite it over the (opaque) background per channel first.
- Linearize each sRGB channel: c/12.92 if c <= ~0.04 else ((c+0.055)/1.055)^2.4; luminance = 0.2126R + 0.7152G + 0.0722B.
- Ratio = (lighter + 0.05) / (darker + 0.05). Thresholds: 4.5 normal text, 3 large text (18px+ or bold 14px+) and UI parts and focus indicators, 7 enhanced.
- Pairs to test in any palette (from the validator): each on-colour vs its fill (primary, secondary, accent, destructive), foreground vs background, card text vs card, muted text vs muted, focus ring vs background at 3:1. Report all failures in one run; return non-zero on failure (the source script always exits 0, a gap).
- When an accent fails, darken/lighten it and record the original (the palette table logs 56 such adjustments (src)).

## 6. Visual craft that is method [R:visual-craft, R:visual-tokens-recipes] WEB,APP,AUDIT
- First classify the screen archetype: showcase/main-task, dense data/dashboard, form/settings, confirmation/dialog, accessibility-critical, utility/transient, reading. Heuristics apply per archetype; skipping one requires a one-line exception: heuristic | why (purpose + evidence) | what was done instead.
- First-glance check: within 3s (showcase, dashboard, dialog) or 5s (forms, settings) (src) a viewer can name the purpose, find the primary action, and see a three-tier hierarchy (hero / second / quiet) even when squinting. Needs a render to claim.
- Hero weight (showcase only): ~1.5x the second tier, highest contrast, 24-48px clearance, at most one effect (src). Dashboard: the one most important number/chart ~1.25-1.5x, others may be equal but never a blind 2x2 grid. Forms: no decorative hero. Dialogs: zero decorative effects, outcome (e.g. amount) and safe exit clearly visible. Accessibility-critical: body 18px+, targets 48-56, contrast toward 7:1, no effects. Reading: typography is the anchor.
- Colour proportion default ~60 neutral / 30 surface / under 10 accent with neutrals tinted 2-6% toward brand hue (src); does NOT apply to strict brand rules, OLED/high-contrast dark, multi-series data, loud directions, accessibility-critical screens.
- Restraint budget per screen: 1 gradient, 1 blur/glass layer, 1 focal animation, 1 accent hue (src); remove any effect whose removal costs no meaning. Clarity beats effect.
- Composition: no cards/boxes/borders by habit when spacing, alignment and type separate groups; balance visual weight top/middle/bottom; improve a single column through composition and type, not added widgets; each component's prominence equals its importance (primary clearly first but not overwhelming).
- Depth: one light direction; elevated = 1px hairline + two-layer shadow; dark mode expresses elevation by lighter surface tint; glass only on floating chrome. Spacing on a 4/8px grid; nested radius = outer radius minus padding; mixed arbitrary radii are a defect. Optical alignment.
- Dark and light: build both only when the product or user needs both, then design and test both as complete experiences; otherwise one line saying why one mode suffices. One product identity: screens differ by archetype and content, never by separate design languages.
- Identity templates (medium/large work, once per product): differentiation analysis (category + use context, audience + mood at that moment, 3 non-contradictory personality adjectives, common competitor patterns, chosen direction + signature, 2-3 deliberately avoided patterns with reasons); one-sentence visual thesis (three adjectives, because <user and trust reason>, identity = <signature>).
- Choosing a signature element: derive it from the gap between competitor patterns and the personality; one element only; specify form, the 3-4 places it appears, the places it must NOT appear (utility, dialogs, forms), and a logo-cover test (hide the logo; is the product still recognisable?) marked spec-only or render-verified.
- Autopilot template signs (each allowed only with a written product reason): unmotivated purple-to-blue gradient on white; generic gradient blob behind a centred hero; every card same radius, same shadow, in three equal columns; default font without hierarchy; emoji in place of structural icons; glass on everything; neon glow without reason; a "welcome back" banner; everything centred; every button the same heavy pill.
- Change-depth audit: layers L1 surface (colour, shadow, border, radius), L2 typography, L3 layout and composition (space allocation, attention flow, removing cards, reflow), L4 component relationships and signature. "New/distinct" passes only with written real change in L1 plus at least two of L2-L4.
- Per-screen blueprint: archetype + anchor + exception; one row per element (tier, type, text, fill, radius, border, shadow, icon-size tokens, padding and hit area); hero size and clearance; signature placement or why absent; all states including offline; reflow at three widths, dark-mode differences, largest font and script line height.

## 7. Direction recipes: structure and adaptation (not the recipes) [R:direction-recipes, R:style-matrix, R:visual-tokens-recipes] WEB,APP,PROMPT
- A direction = fixed field set: colour seed (base lightness range, hue range, saturation range, where the accent may appear), type family class, shape and depth (radius ladder, border, shadow/glow), one signature, imagery rule, do-not-use contexts, motion envelope.
- Derive for a product: pick from product type, audience and task; check the direction's do-not-use list AND the style table's veto (accessibility, performance, trust-critical finance/health, weak phones, long text, children, elderly); any hit vetoes; exactly one direction per product.
- Adapt: change at least two fields for this product and write why (else it is a blind copy); turn colour seeds into real values only in the palette table and measure contrast; Latin type pairings require the script check for other scripts.
- Dials (1-10): variance (centred-minimal to bold-asymmetric), motion (micro only to choreography), density (spacious to dashboard). Density maps to spacing ranges 24-96 / 16-64 / 8-32px (src). If the user gives none, set them from the product and state them in one line. Dials constrain direction and motion, never override them.
- Large-work presentation plan: one focal moment (what, where, ms, reduced-motion alternative); direction + one-line reason + veto check; the 2+ customisations; where smart cues (auto-detect tag, prefill, progress, undo) appear; 3-5 polish upgrades; benchmarks labelled verified only if viewed this session.

## 8. Motion rules [R:motion-and-charts, D:motion.csv, D:app-interface.csv, D:ux-guidelines] WEB,APP
- Same easing family product-wide; duration scales with distance (0-4px 80-120ms; 8-24px 150-250ms; sheet/page 250-500ms), element size (icon/chip/button 80-150; card 180-280; sheet/modal/full 280-450) and importance (frequent utility 0-120, never blocking; one hero moment 300-600 per screen) (src).
- Animate transform and opacity only, never width/height/top/left/margin; 1-2 animated things per view; exit ~60-70% of enter (src); hover displacement under ~2px.
- Every animation interruptible and non-blocking: on rapid change cancel the old one and set the final state directly; never make correctness depend on animation-end events.
- Reduced motion: entrances off, parallax and shimmer static, final state rendered. Continuous/looping motion limited; auto-rotating content has visible pause, previous/next, stops on focus, hover, offscreen and hidden tab, and cleans up timers. Skeleton: content-shaped, sweep 1.2-1.6s (src), not an opacity pulse; frame budget ~16ms on low-end phones outranks aesthetics.

## 9. Charts rules [R:motion-and-charts, D:charts.csv] WEB,APP,AUDIT
- Pick by the data question: trend -> line; compare -> bar (sort descending); part-to-whole -> pie/donut only for <=5 slices with clear differences, else horizontal bar; correlation -> scatter; intensity -> heatmap; geography -> choropleth; flow -> funnel/sankey; target -> bullet/gauge; forecast -> line + band; hierarchy -> treemap <=3 levels; bridge -> waterfall <=12 bars; multi-metric -> radar <=8 axes; finance OHLC -> candlestick (src thresholds).
- Fallbacks from the when-not column: under 4 points -> stat card; over 15 categories -> sortable table with search; over 6 line series -> noise; under ~20 cells -> bar not heatmap. Volume -> renderer: under ~1000 points vector, above that canvas + downsampling, above ~10000 aggregate (src).
- Every chart: non-colour encoding (line styles, patterns, direct labels; never red/green alone), legend near data, tooltip on hover + tap + keyboard focus, data marks 3:1 and text 4.5:1, visible data table and a one-line insight, defined empty/loading/error states, entrance animation off under reduced motion. Each row carries an accessibility risk grade (low/conditional/high).

## 10. Decision logic of the big tables (logic only) [D:products, D:ui-reasoning, D:styles, D:colors, D:typography, D:landing, R:industry-playbook-192, R:style-matrix, R:typography-pairings-74] WEB,APP
- Key: a product type (192 rows) is found by keyword match; it joins to a reasoning row, a palette row, style rows (by id/alias), a landing pattern (by alias) and type pairings (by mood keywords). Product row: primary style pair, secondary styles, landing pattern, dashboard style, colour focus, key functional considerations (category must-haves such as map-first layout or seat map).
- Reasoning row: style priority, colour mood, type mood, key effects, anti-patterns, severity, and JSON decision rules: must-have constraints plus conditions (most common: trust needed, mobile, UX-focused, conversion-focused, light mode needed, content-focused, low performance) whose actions override style, add constraints, set pattern or force mode.
- Style row: best-for vs do-not-use contexts, light/dark support, performance cost with drivers (blur, animation, 3D, WebGL), accessibility risk with required checks (text contrast, keyboard, visible focus, reduced motion), mobile fit, conversion fit, complexity, a pass checklist, lifecycle status with replacement. Veto: high cost for weak devices, high risk for critical users.
- Palette row: every semantic role with its on-colour; justification = category mood (trust -> cool blue/navy, appetite -> warm, calm health -> soft cool/green) + contrast-adjusted accents.
- Landing row: ordered sections, where the primary action sits and repeats, colour strategy, effects, conversion checks (action label 4.5:1 on its fill, skip for immersive intros, label live data as live only with a current source).
- Avoid columns mix look vetoes (no neon/heavy motion in health, no playful look in finance/legal/government) with functional vetoes (hidden fees, no search, no status, colour-only indicators) - port the functional ones as checks.

## 11. Generator pipeline [SC:design_system, SC:core, SC:reasoning_contract, SC:search] WEB,APP (tooling)
1. Search the product table with the query; take the category. Retrieval = BM25 with synonyms and stopwords; abstain when score is under a per-domain floor or too few query words are covered, and suggest close names instead.
2. Load that category's decision rules; parse them with a closed grammar (known condition names, fired by whole-word signal phrases in the query; actions limited to constraint/style/pattern/mode with validated values; never evaluated as code).
3. Apply dials: variance biases style search toward minimal or bold keywords; motion picks a motion tier snippet; density overrides the spacing scale.
4. Multi-domain search (style with priority hints, colour, typography, landing, effects); pick the best match per domain by priority keywords.
5. Resolve light/dark FIRST (style dark-first flag + explicit query words), then take the highest-ranked palette agreeing with that mode; if none, derive a dark palette (brand kept, fixed dark surfaces, accent chosen to reach 3:1 on background); drop anti-patterns that contradict the mode.
6. Assemble pattern, style, colours, type, effects, anti-patterns, checklist; print as box or markdown; optionally persist a master file plus per-page override files (page type detected from the page name), skipping existing files unless forced.
- Stack advice is filtered to the declared current version; legacy rows only when asked, with successor guidance.

## 12. Validators worth re-implementing [SC:validate_brain, SC:validate_data, D:data-provenance.json, D:catalog-summary.json] CORE,AUDIT
- Skill lint: logic file is well-formed, version labels agree across entry/index/logic, every referenced capability and file exists, every section cross-reference resolves, logic file contains no hex values or data tables and stays under a size cap, stray-script characters only inside code spans, every numeric example produced by a tool is recomputed by running it. Claims structure only, not design quality.
- Data lint: required columns present, no duplicate keys, JSON columns parse, palette pairs pass contrast, cross-table references resolve, snapshot hashes and declared counts match, font licences known, icon names exist upstream.
- Provenance: each data claim has a verified date and freshness window (365 days manual-verified, 90 needs-review (src)); "manual-verified" cannot rest on derived sources only; expired = stale.

## 13. Guideline tables as audit checklists [D:ux-guidelines, D:app-interface, D:react-performance, ST:*] AUDIT,WEB,APP
- Rows = issue, do, don't, good code, bad code, severity (critical/high/medium/low). Audit by walking critical then high rows and citing the issue name; stack rows also carry applies-to version and verified date - confirm the project's version first.
- Web/app must-checks (from the rows): icon buttons and inputs named; visible labels (no placeholder-only); targets and spacing; gesture actions have visible alternatives; drag has single-pointer alternative; focus not obscured by sticky bars; error summary focusable; accessible authentication (paste, password managers); no redundant re-entry; consistent help location; reserved image space (no layout shift); no horizontal scroll at phone width; long tokens wrap; essential text never truncated; chip groups reflow before labels shrink; live badges announce politely; safe-area insets; back behaviour preserved; screen state preserved on return.
- Stack rows reduce to portable principles: server/static by default and hydrate only interactive parts; derive instead of syncing state; effects only for external sync with cleanup; stable list keys; virtualize long lists; keep blocking work off the UI thread; theme colours via resources/variables never hardcoded; one pinned library version.

## 14. Evidence wording [R:examples] CORE,AUDIT
- "Tool-verified" only with the command shown; values from reference data are labelled as such; recalled benchmarks are labelled unverified recall; without a render the verdict is "spec-approved, render-unverified"; never write "passed/approved" without render or interaction evidence.
- Micro change answer = size line + the change + one evidence line, nothing else. Placement before decoration: put the primary action where the thumb reaches before styling it.
