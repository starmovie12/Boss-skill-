## A. Output contract and self-check (CORE)
- [S2-P05-1560 | CORE] The output shape is binding. Start with the deliverable itself, not commentary. When several shapes apply (UI + API + realtime), compose them in order.
- [S2-P05-1560 | CORE] No truncation: search the output for "...", "etc.", TODO stubs, "same as above" and "rest unchanged" standing in for content. Any hit means the work is incomplete.
- [S2-P05-1560, S2-P05-1602 | CORE] Manifest rule: list the planned files and deliver each one complete; never point one file at another for missing content. A planned file that is not needed is named and skipped with a reason, so delivered + skipped = planned.
- [S2-P05-1791 | CORE] Self-check before emitting: (1) every required field of the shape is present; (2) no placeholders, every file complete, skips named; (3) no preamble; (4) every example agrees with the rules and format; (5) machine-read output validates against its schema, with no stray prose or fences; (6) the quality and design pre-checks passed for exactly what ships. Any fail: fix first.
- [S2-P10-2810 | CORE] Honesty about the guidance itself: state confidence, mark unproven claims, treat each delivered design or spec as a hypothesis with a named way to check it, and let evidence override the rules.

## B. Prompt and spec writing for agents (PROMPT)
- [S2-P05-1731 | PROMPT] Prompt order: (1) role + single goal; (2) rules, then sub-sections; (3) reasoning order; (4) exact output format ("respond only as ..."); (5) several examples consistent with rules and format; (6) grounding context; (7) closing restatement of the key instruction. An example that contradicts a rule degrades behavior: check every pair.
- [S2-P05-1731 | PROMPT] Autonomous-agent reminders: (a) persist until the task is actually resolved; (b) when unsure of a file, value or state, check it with a tool, never guess; (c) plan before each significant action and reflect on the result after.
- [S2-P05-1731 | PROMPT] Models read literally and weight later instructions more. When behavior is wrong, first look for a vague or conflicting instruction before adding text. On conflict, state which rule wins (most specific or most recent). Pair a rule with one input/output example. Prefer "do X" plus a short note of the failure to avoid over walls of prohibitions.
- [S2-P05-1731 | PROMPT] Long context: put the key instructions before AND after the material; say whether outside knowledge is allowed or only the given material; have the model quote the relevant passages, then reason, then answer; never bury the question mid-block.
- [S2-P05-1731 | PROMPT] Code edits: name the file, show enough unchanged context around each hunk, mark additions and removals, and never rely on line numbers. Use a format the downstream tool actually parses.
- [S2-P05-1731 | PROMPT] Machine-read output: demand "only valid JSON matching this schema, no prose, no fences". Spell out every field, its type and whether it is optional. Parse defensively: strip fences, validate, handle failure.
- [S2-P05-1777 | PROMPT] Role prompts: seniority + domain + bar, then what the role refuses to ship, then format, then context. A role is only a quality lens: it never unlocks crossing safety or honesty rules.
- [S2-P05-1627 | PROMPT] AI-feature prompts: the system prompt is static with no user data. User input is sanitized and delimited. Structured output is validated before use. Fallback chain: other model, then graceful degradation. Log tokens per request, filter content before display, flag injection attempts.

## C. Acceptance criteria and the requirements-spec engine (PROMPT, AUDIT)
- [S2-P08-2275 | PROMPT] Role test for any spec or work order: could an engineer, designer, QA lead and legal reviewer each act on it with zero clarifying questions? Every place a reader must guess is a defect.
- [S2-P08-2284, S2-P08-2441 | PROMPT,AUDIT] Requirement tests: Atomic: split any requirement joining two behaviors with "and"; Testable: has a pass/fail criterion; Unambiguous: no fast/scalable/soon/some/many/intuitive/seamless/robust/lightweight without a number or definition; Necessary (traces to a goal) and feasible at scale; Prioritized must/should/could/won't; won't items are written as non-goals; Traceable to a metric, test or owner.
- [S2-P08-2441 | PROMPT] Requirement record: id, statement, priority, acceptance criteria. The criteria hold an exact threshold, the measuring setup (device, network, tool) and the fail condition. Source example: p95 under 400 ms on a named low-memory phone over a slow network.
- [S2-P08-2284 | PROMPT] Further laws: state what and why; prescribe how only when the method is itself required. Every flow names its error, empty, loading, offline, throttled, partial and abuse states. Numbers carry unit, currency, timezone and baseline. Every assumption and dependency is written down.
- [S2-P08-2300..2432 | PROMPT,AUDIT] Canonical sections (23); any that does not apply is marked "N/A, reason", never dropped:
  - 1-5: document control (version, status, owner, reviewers, changelog, source order); summary (outcome + why + top metric); problem, solution-independent, with evidence and cost of inaction; goals as outcomes + explicit non-goals; metrics (north star, supporting, guardrail, each with target, method, source, horizon).
  - 6-10: users incl. the median user's worst device, network, locale and accessibility; stories with acceptance criteria incl. undo/cancel/recover/report; numbered functional requirements covering CRUD, roles and state transitions; non-functional targets as numbers on a named baseline (perf, scale, availability, security, privacy, a11y, l10n, compatibility, cost, observability); flows and every screen state with copy, keyboard, screen reader and reduced motion.
  - 11-15: data entities (typed fields, indexes for real queries, retention, personal-data class); system/APIs (payload schema, auth, idempotency, rate limit, dependency-down behavior); economy if any (value sources, prices, fees, solvency, store rules); edge cases (empty, max, concurrent, conflicting, interrupted, offline, clock skew, duplicate, race); dependencies and assumptions.
  - 16-23: risks (likelihood, impact, mitigation, owner); trust and safety incl. minors; legal per jurisdiction; rollout (flags, kill switch, migration, tested rollback); analytics events one-to-one with metrics; open questions (owner + needed-by date); definition of done as a checklist anyone can verify; glossary.
- [S2-P08-2453 | PROMPT,AUDIT] Completeness gate, 14 checks; any fail blocks sign-off: sections present or N/A; requirements well-formed; non-functional numbers on a baseline; metrics tied to events; unhappy states; edge cases; assumptions/dependencies/risks; safety and legal; closed economy if present; rollback; owned open questions; done checklist; glossary; units, with no vague words left.
- [S2-P08-2472 | PROMPT] Build order (8 steps): 1. Restate goal, constraints, source order and conflicts; 2. Ask only the load-bearing unknowns; record the rest as assumptions or open questions instead of stalling; 3. Draft the sections in order; 4. Ground every number in code, platform rules and cost; 5. Self-audit; 6. Fix blocker/critical/major findings; 7. Run the gate; 8. Finalize version and owner; list the open questions.
- [S2-P08-2484 | PROMPT] An unvalidated problem gets a discovery plan first (questions, experiments, kill signal). Estimates are ranges with assumptions and the biggest unknowns. Changes to an existing system specify backfill, dual-write or shadow-read, cutover, compatibility, rollback and decommission, plus behavior in half-migrated and mixed-version states.

## D. Audit of a spec or document (AUDIT)
- [S2-P09-2522 | AUDIT] The output is a findings list with severities and corrected text; never "looks good". Read as engineer, QA, designer, legal reviewer, abuser and finance owner. Catch small and big flaws in one pass, and apply this to your own drafts too.
- [S2-P09-2534 | AUDIT] Defect taxonomy D01-D20:
  - D01-D06: missing section; vague wording; untestable requirement; unquantified metric (no number, method, horizon or event); missing state, edge case or failure mode; missing non-functional target.
  - D07-D12: contradiction (state which source wins); unstated assumption or dependency; missing non-goals, or goals written as activities; missing definition of done; abuse/security gap (gameable mechanic; client-trusted money, score or auth); privacy/legal gap.
  - D13-D20: economy flaw (mintable, negative-sum, no losing-side experience); open question without owner or date; feasibility/cost risk at 50x; traceability gap; numeric hygiene (unit, currency, timezone, baseline, off-by-one tiers, stale values); UX gap (copy, a11y, TBD); cross-reference/structure defect; second-order effect that defeats its own goal.
- [S2-P09-2558 | AUDIT] Section pass: ask one yes/no question per canonical section ("goals measurable, with explicit non-goals?", "every metric matched by an analytics event?"). Every "no" becomes a finding with its location.
- [S2-P09-2585 | AUDIT] Small-flaw sweep: vague words; unitless numbers; one thing with two names; stale values; inconsistent thresholds; broken references; duplicate ids; undefined acronyms; TBD/"..."/"etc." in place of content; wrong-language copy; a metric without an event; a term used before it is defined.
- [S2-P09-2593 | AUDIT] Big-mistake sweep, asked of each load-bearing claim: survives 50x load and its cost? inflated reach claim? bot-farmable? role enables abuse? value mintable? races, clock skew and duplicates handled? injection-safe, private messages unread? legal scale thresholds acknowledged? minors protected? Then pair findings that combine into a worse failure. Each killer is a blocker or critical with the architectural fix.
- [S2-P09-2606 | AUDIT] Severity with written criteria:
  - BLOCKER: ships broken or unsafe, or a legal/economic time bomb (mintable currency, private-content scanning, unscalable core claim, no minor protection, no rollback). Cannot be approved.
  - CRITICAL: core capability unspecified or wrong (missing non-functional target on a core path, missing failure mode on a key flow, unquantified north star, core contradiction). Fix before sign-off.
  - MAJOR: gap that causes rework or an incident (missing edge case, vague requirement, hidden dependency, traceability gap). Fix before build.
  - MINOR: secondary gap that does not block the build.
  - NIT: hygiene (missing unit, stale number, broken reference, undefined acronym). Fix in the cleanup pass.
- [S2-P09-2615 | AUDIT] Fix protocol, 7 fields per finding: (1) location, quoted; (2) category id; (3) severity; (4) the problem; (5) impact if unfixed; (6) paste-ready corrected text at requirement standard; (7) the metric, test or owner it now traces to. When a fix needs the owner's decision, write a tracked open question with options and a recommendation instead of guessing.
- [S2-P09-2627 | AUDIT] Report order: 1. Header: document, version, date, auditor, source order; 2. Scorecard: counts per severity, gate result, one-line verdict "READY" or "NOT READY: N blockers, M criticals"; 3. Section coverage map: present / N-A with reason / missing; 4. Findings, by severity then section; 5. Compound risks, each with the one change that breaks the chain; 6. Open decisions: owner, options, recommendation, date; 7. The explicit bar: zero blockers and criticals, every major fixed or tracked, gate passed, stress checks survived. Say whether it is met.
- [S2-P05-1634 | AUDIT] Security-report variant. Bands (source's): critical 9+, high 7-8.9, medium 4-6.9, low 0.1-3.9, info. Per finding: score + vector, standard category, file:line, exploit scenario, impact, minimal proof, complete fixed code, and a test proving the fix.

## E. Phone-only operations (WEB, APP)
- [S2-P06-1949 | WEB,APP] Phone-only user: never give a desktop-only step (no "open your computer terminal", no local emulator, no desktop IDE build, no PowerShell).
- [S2-P06-1949 | WEB,APP] Tool map: on-device POSIX shell for git clone/commit/push, light scripts and file ops; a hosted notebook for Python, server-side and bulk-data jobs; a cloud build service for every app build (development, preview, production profiles) and over-the-air updates.
- [S2-P06-1949, S2-P06-1829 | WEB,APP] Before adding a package: read the manifest to confirm it is not already installed; install with the SDK-aligned installer; if it needs a custom native build the cloud service cannot do, flag it as a blocker. Deliver whole copy-paste-ready files, never fragments.
- [S2-P05-1686 | WEB,APP] Phone-shell scripts: POSIX first; honor the prefix variable; no hardcoded system paths; declare dependencies and fail early; fallbacks for non-portable flags; assume a slow metered network (retry with backoff, honor proxy variables); standard per-user config/cache/data directories.
- [S2-P07-2173 | WEB,APP] Solo operator: when the target architecture is more than one person can run at launch, keep its principles, ship a reduced version, and always say which parts are stubbed versus live.

## F. Stack-neutral app and web build rules (WEB, APP)
- [S2-P06-1829 | CORE] Before writing code, read the manifest and neighboring files to confirm framework version, styling system and installed libraries. Follow the repo's aliases and token names. Live code beats tutorials, rule files and playbooks.
- [S2-P06-1839 | APP] Live lists: virtualize, memoize rows, stable keys, cap the mounted window (source: ~200) and page older items back in. Keep the reader's scroll position when new items arrive; batch bursts. Source target: 60 fps on a 3 GB phone.
- [S2-P06-1839 | APP] Motion on the UI thread with named spring/easing parameters; burst effects mutate refs, not state. Every animation has a reduced-motion fallback. Changing numbers use fixed-width digits, so there is no layout shift.
- [S2-P06-1839 | APP] Bottom sheets: a fast swipe dismisses, a slow drag snaps back, and the inner scroll must not fight the sheet drag (resolve the gesture conflict explicitly). The chat input tracks the keyboard so the last message stays visible.
- [S2-P06-1839 | APP] Native feel: navigation sits above the home indicator; the input accounts for keyboard + indicator; semantic haptics; correct status-bar style; no pull-to-refresh on live streams; content selectable, chrome not. Own a small base component layer whose variant and size props map to tokens.
- [S2-P06-1910 | WEB] Web: Every async route has loading, error and not-found siblings, with skeletons shaped like the content; Images carry width, height and alt; the main above-fold image gets priority; fonts use swap; Every page sets title, description and social metadata, and declares its cache strategy; Server-first rendering, with client code only where interaction needs it; Strict schema validation on every input; server secrets never in client-exposed variables; Optimistic mutations roll back on error.
- [S2-P05-1602, S2-P06-1910 | WEB,APP] Handler order: authenticate, abuse check, rate limit, validate, logic, audit record, response. The server decides money, score, rank and authorization.
- [S2-P05-1585 | WEB] Single-file page: doctype + lang, head (charset, viewport, description, social tags), style, semantic body, script. Style order: tokens, dark, reduced-motion, reduced-transparency, reset, type, layout, components with all states, keyframes, mobile-first responsive. Script: exact ms timings, debounced handlers, no color literals.
- [S2-P05-1667 | APP] Native spec: versions and minimum OS; a native-module table (purpose, permission); 3 build profiles with distinct app id and endpoint; safe-area insets for notch and gesture bar; deep-link domain, scheme and routes; secure credential storage.
- [S2-P07-2197 | WEB,APP] Under load, degrade in visible stages (indicator, batched display, pause on scroll-up with a "new items" chip, honest send delay); never silently hide or drop content. (QUARANTINE unit; method only.)

## G. Testing and localization (CORE, WEB, APP)
- [S2-P06-1997 | CORE] Test by risk and layer: unit tests for logic; integration tests for seams (DB, API, auth, third parties); end-to-end tests for the few critical journeys; load tests for concurrent or realtime paths.
- [S2-P06-1997 | CORE] Always test unhappy paths: error, empty, offline, permission denied, race, duplicate, malformed input. Tests are deterministic (no time, network or order dependence) and run as a merge gate. Coverage is only a diagnostic: an untested critical path fails at any coverage.
- [S2-P05-1675 | AUDIT] Load-test cohorts: read-heavy, write-burst, parallel writers to one record, auth flow, plus hostile cohorts (injection, id enumeration, rate-limit edge, credential stuffing). Numeric pass criteria (source: p95 < 500 ms, p99 < 1500 ms, legit error rate < 0.5%, zero corruption). Any miss blocks shipping.
- [S2-P06-1978 | REF] ML/LLM features: define the eval (test set, metric, threshold) before building and run it in CI. Version data, models and prompts.
- [S2-P06-2006 | WEB,APP] Localization:
  - Externalize every string; translate whole phrases with placeholders, never concatenated fragments.
  - Support plural, gender and locale formats for number, date, currency and measure.
  - Leave room for text expansion (source: ~30% longer) and mirror layouts for RTL.
  - Declare the source locale and the fallback chain.
  - A deliberately single-language product is a product decision, not a defect.

## H. Diverge then converge, and the user's choice (WEB, APP, PROMPT)
- [S2-P10-2673 | WEB,APP,PROMPT] Phase 1, diverge: generate genuinely different directions, bound only by safety, legality, honesty, wellbeing and minors; output shapes constrain format, never the idea. Phase 2, converge: take the strongest viable direction and only then apply rules, gates and shapes to harden it. Never use gates during divergence to prune.
- [S2-P10-2718, S2-P10-2688 | WEB,APP,PROMPT] How many: the source asks for at least 3, and in its gate exactly 3: literal (the exact ask, optimized), enhanced (the same idea extended forward), reframed (a different core mechanism from first principles). At least one breaks the obvious frame.
- [S2-P10-2757 | WEB,APP,PROMPT] How they must differ: in core mechanism or central assumption. A renamed button, a recolor or a rephrasing does not count. Never pad to a count: if only 2 or 1 real options exist, present those and say so.
- [S2-P10-2688, S2-P10-2770 | WEB,APP,PROMPT] How one is chosen: the user picks; build exactly that. Offer the bigger move once, then do not substitute, re-argue or widen scope. If the user already gave an explicit instruction, follow it without halting (this corrects the source's always-halt rule, which is CONFLICT).
- [S2-P10-2743 | WEB,APP,PROMPT] Trigger: the first idea is the expected template answer. Pick a few sparks (not all): inversion (design the failure, then flip it), a distant-domain analogy, remove or tighten a constraint, delete the feature, an ideal-experience pass, a second use, a borrowed perspective.
- [S2-P10-2708 | CORE] When a convention blocks a clearly better result, name the rule, show the alternative and its tradeoff, and propose it. Never silently obey or silently break it. Safety rules are never negotiable.
- [S2-P10-2779, S2-P10-2788, S2-P10-2728 | WEB,APP] After the literal deliverable: optionally add one adjacent bigger move, labeled speculative if unproven. Name one deliberate signature detail and why it fits. Check the design does not dead-end the likely next needs, without building them unasked.
- [S2-P05-1698 | WEB,APP] Visual direction: declare one direction with a one-sentence rationale, then check every token, typeface, spacing unit and motion choice serves it; no blended or generic fallback. The 15 named presets are QUARANTINE-DESIGN; keep only the commit-and-verify method.
- [S2-P10-2797 | PROMPT] If no defined output shape fits a deliverable, define a new shape explicitly rather than forcing a bad fit.

## I. Project-module method (CORE; product canon quarantined)
- [S2-P07-2052, S2-P07-2087 | CORE] A project module records the ground truth (product, exact stack versions, repo, dead plans to ignore) and a ranked source-precedence list with live code first. Its concrete values override universal defaults, and it loads only for that project.
- [S2-P07-2226, S2-P07-2134 | CORE] Conflict ledger: each entry has an id, the competing sources, and either a resolution naming the winning source or an "open" status saying what the owner must confirm. Never silently pick on an open entry; ask before building on it.
- [S2-P07-2052, S2-P07-2214 | CORE] Code requests: fetch the repo fresh; read the target file plus everything it imports; edit the real file and return it whole with its path; flag code-vs-spec divergence; confirm before extending legacy features; rename opportunistically, never in bulk unasked.
- [S2-P07-2087 | WEB,APP] Contrast reasoning: judge each text/fill pair by its measured ratio. A brand color that fails as text stays fill-only, carrying dark text; failing pairs are listed as banned. Both themes resolve through one palette lookup.
